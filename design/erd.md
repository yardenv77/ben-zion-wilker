# Entity-Relationship Diagram (Real Database Schema)

**Source:** interactive SVG diagram embedded in `erd.html` (open it in a browser). Unlike `design/class-diagram.html` — which models the UML domain model (inheritance as generalization arrows, many-to-many relationships with attributes as UML association classes) — this diagram shows the database exactly as `scripts/create_database.sql` actually creates it: 23 real tables, their real columns and SQL types, real `FOREIGN KEY` constraints, and real `CHECK` constraints.

All 23 tables are laid out on a single canvas in the same four spatial clusters `class-diagram.html` uses (Sales/Tendering, Procurement & Partners, Field Execution, Finance & Risk, with `Project` as the connecting hub), so the two diagrams stay easy to compare side by side. Each table box lists its columns with `PK`/`FK` prefixes marking the primary key and foreign key columns; a `{CHECK}` suffix marks a column constrained by a `CHECK` clause. Lines are the real `FOREIGN KEY` constraints, each a simple N:1 (child FK column -> parent PK) — there is no UML multiplicity notation here because none is needed at the physical level.

## How this differs from `design/class-diagram.html` / `design/class-diagram.md`

1. **Table-per-subclass instead of UML generalization.** `BusinessPartner` -> `Supplier` / `Subcontractor` and `FinancialSecurity` -> `BankGuarantee` / `InsurancePolicy` are not drawn with a generalization arrow here. They are real, separate tables (purple header, `«table-per-subclass»`) whose own primary key is also a foreign key back to the base table (`PK/FK business_partner_id`, `PK/FK financial_security_id`) — the inheritance relationship *is* that FK, per `PATTERNS.md`'s table-per-subclass pattern.
2. **Real join/link tables instead of UML association-class notation.** `SupplierPriceQuote`, `Attendance`, `EquipmentUsage` and `EquipmentAssignment` (teal header, `«join / link table»`) are ordinary tables with their own surrogate primary key plus one `FOREIGN KEY` per side they connect — not a dashed line to a diamond the way an association class is drawn in the UML diagram.
3. **Enumerations as `CHECK` constraints, not boxes.** Every enumeration listed in `CLAUDE.md`'s Enumerations table (`TenderStatus`, `ProjectStatus`, `PartnerStatus`, `POStatus`, `ClosureReason`, `EmployeeRole`, `EmployeeStatus`, `WorkLogStatus`, `EquipmentStatus`, `SecurityStatus`, `PaymentRequestStatus`, `DocumentType`, `SupplierPaymentStatus`) appears here as a plain `NVARCHAR` column on its owning table, tagged `{CHECK}` — never as a separate box and never as a foreign key to a lookup table, per `PATTERNS.md`'s "Enumerations — CHECK Constraint, Never a Lookup Table" rule.

This diagram is a companion to, not a replacement for, `design/class-diagram.html`: the class diagram remains the analysis-level UML domain model; this ERD is its physical/relational realization as actually scripted in `scripts/create_database.sql`.
